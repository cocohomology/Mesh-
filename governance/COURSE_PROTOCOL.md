# Course Protocol

## 目的

本文件定义课程如何运行。它讨论的是“怎样学习”，而不是“学习什么”。

课程必须能够脱离任何单一聊天窗口持续推进。所有重要状态、决策、争议和下一步，都应最终写回仓库。

## 一、标准推进循环

每个教学循环原则上经历：

1. **定位**：读取 `PROGRESS.md`，确认当前模块、当前 Note、开放问题与下一步。
2. **准备**：检查所需前置知识、参考资料、历史讨论和已有反馈。
3. **教学**：围绕当前问题展开完整讲解，而不是机械追赶大纲。
4. **追问**：显式辨认定义、假设、定理、算法、反例、工程现象之间的联系。
5. **互动**：用户提出质疑、联想、工程经验或数学补充；助手必须判断这些是否改变课程结构。
6. **沉淀**：将成熟内容写入 Note；将未成熟但重要的内容写入 Discussion。
7. **校准**：根据用户反馈调整深度、顺序、符号、例子、证明或实现安排。
8. **交接**：更新 `PROGRESS.md`、`TASKS.md`，必要时更新 `DECISIONS.md` 与大纲。

## 二、一次聊天并不等于一个教学单元

禁止为了“这一轮聊完”而强行完成一个主题。

一个主题可以跨多次聊天；一次聊天也可以只解决一个定义、一个反例或一个关键疑点。课程进度以知识结构是否闭合为准，而不是消息数量。

## 三、掌握标准

对于核心概念或算法，至少尝试达到以下层次：

- 能说明对象与假设；
- 能说明核心数学结构；
- 能理解或重建关键推导；
- 能解释算法为什么成立；
- 能识别其数值、组合、几何或模型层面的失效；
- 能比较推广版本改变了什么结构；
- 对重要算法，能够实现、实验或阅读成熟实现。

仅会调用库接口、背诵流程、照抄公式，不视为真正掌握。

## 四、数学与工程的连接规则

课程禁止形成“前半本数学，后半本算法”的断裂结构。

每个核心算法都应尽可能建立：

`Algorithm <-> Theorem <-> Structure <-> Failure <-> Generalization`

同时，每个抽象数学结构也要追问：

- 它在网格中具体表示什么？
- 哪些算法真正依赖它？
- 它解决了什么工程困境？
- 若忽略它，工程上最常见的后果是什么？

## 五、动态大纲

`syllabus/OUTLINE.md` 是动态地图，不是合同。

允许：

- 因一个基础漏洞回退；
- 因重要联系提前插入模块；
- 合并原本分开的主题；
- 将一个模块拆成理论线和工程线；
- 暂停低收益内容；
- 因研究问题开启支线。

任何明显改变课程路线的调整，应记录到 `DECISIONS.md`。

## 六、课程节奏

默认采用“主线 + 侧路”模式：

- 主线保证课程持续向前；
- 侧路用于追踪重要数学联系、历史背景、实现问题或研究性问题；
- 侧路过深时，应登记为独立任务，避免主线永久失焦。

## 七、代码与实验

代码不是每篇 Note 的必需品，但以下情形优先安排实验：

- 理论结论具有明显数值边界；
- 算法存在经典退化或失效场景；
- 多个等价理论刻画需要直观验证；
- 数据结构选择直接影响算法复杂度；
- 工程实现与数学定义存在缝隙。

实验应尽量服务于理解，而非追求项目规模。

## 八、完成条件

一个 Module 可以被标记为“阶段完成”，但不意味着永久封闭。

完成至少要求：

- 主 Note 可独立阅读；
- 核心术语与符号稳定；
- 核心数学—算法联系已建立；
- 关键开放问题已明确记录；
- 用户反馈中的主要问题已处理；
- 后续模块需要的接口已经清楚。
